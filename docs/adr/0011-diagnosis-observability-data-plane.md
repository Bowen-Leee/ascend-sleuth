# 诊断观测数据面：条目增量进期文件，真值分两条通道

## 状态

提议

## 背景

本仓现在能记下一次诊断的过程，却回答不了三个问题：这一次诊断值不值、这条知识还有没有用、流程哪里在浪费。事实如下，都可现算。

- **结局侧没有输入**。三期 live 快照的 `feedback_capture` 都是 `{resolved: 0, not_resolved: 0, partial: 0}`（`metrics/timeline.yaml` 的三条 live 期），命中率、误诊率、校准因此只能标不可解读。同时 `scripts/settle_trace_feedback.py:16-19` 记着「数据都在 traces 里，但没有任何脚本产出它」。
- **指标大面积空转**。面板的 27 个指标标签里只有三个真消费点（`scripts/metrics_health.py`、`scripts/evolution_health.py`、self-evolve 的漂移判读）；`triage_miss_classes`、`triage_miss_sessions`、`reference_outcomes`、`stop_reasons`、`parallel_group_events`、`considered_candidates_events` 有产出、在白名单里，8 期期文件一个都没写过；`attribution_ratio` 的读端读的是 `verdict`，生产端写 `attribution_kind`，恒为 0（`scripts/trace_metrics.py:240-243` 对 `scripts/component_tally.py:54-58`）。
- **同一个量有多处定义**。「命中」在案例本体的 `confidence.hits`、期文件的 `tier2_hit`、`scripts/trace_metrics.py` 的现算值三处各有口径。本条已在本仓吃过一次（`docs/adr/0004-capacity-governance.md`）。
- **条目级观测没有落点**。期文件里唯一按 id 记的是 `metrics.reference_detail`；案例侧没有对应块。上一稿曾决定不把这类观测扩充进仓库的指标字段，其假设是「案例选中史只属于这台机器」；现在需要它来回答「哪些条目被检索却从没解决」。
- **外部真值通道的现状**：全仓没有 `api.github.com` 调用；6 处 `gh` 调用都不读 issue 或 PR 的 `state`（唯一读外部结局的是 `scripts/ev_proposal.py:334`，对象是改进项指针）；案例 `validation_record.consistent` 迄今全为 0。
- **无效探索没有对应概念**。全库没有任何一处统计一次诊断内部的无效步骤；轨迹里为这件事预留了三个字段（顶层 `stop_reason`、事件级 `parallel_group`、`considered_candidates`），但打分本体未落地，闸门是「任一部署机轨迹达 30 条且反馈捕获率大于 0」（`docs/adr/0009-counterfactual-replay-exploration-policy.md` 的重评条件），当前不满足。
- **形态约束**：期文件的 `metrics` 段受 `scripts/verify_metrics.py:40-60` 的白名单约束；面板的期文件解析器是手写的，会把 `metrics` 上下文里缩进不超过四层的行折进 `metrics`（`dsh-plugins/ascend-panel/panel-host.js` 的 `parseTimeline`）；「生成物里不写数字」只约束生成物（`CLAUDE.md:117`），源文件如仓根的 `ingest-state.json` 含数字且已上仓；读数按部署分家（`docs/guide/git-workflow.md:64-65`）。

设计与规格在 `docs/mechanism/diagnosis-observability.md`，本文承载取舍。

## 决定

我们决定把条目使用增量作为期文件 `metrics` 段的一个新块随周批上仓、不写进案例文件，把结局真值分成外部自动对照与现场人工确认两条通道分别计，并只落地无效探索里可离线重算的那一半。

## 被否决的替代方案

- **把条目使用增量写进案例文件**（否决）。好处是跨机器可见、直接参与退休判断。代价是每次结算都改知识文件、并发在嵌套 YAML 上撞行，且把「这台机器的使用史」混进知识本体，`confidence` 的「现场确认解决」与「被选中」两种含义会混成一个数。
- **按条目一个文件**（否决）。好处是不同条目互不相干。代价是同一个 id 的历史跨期写进同一文件，冲突时没有确定性重建命令，取一边等于静默丢数；本仓给出过的同形先例是 `postmortems/2026-Q3/`，它的每个文件一次写定、不再追加。
- **做成仓根状态文件**（否决）。好处是名字上不再属于指标。代价是它会与期文件重复定义同一个量，而两个落点必有一处先腐烂。
- **每次诊断的指标单独开一个 PR**（否决）。好处是证据与结论同行。代价是轨迹含客户现场信息、进 git 要先逐单脱敏，且 PR 量从每周一次变成每单一次，而每周一次是当前能维持的门控节律。
- **只保留周期节律**（否决）。好处是冲突处理与门控节律不变。代价是条目级观测进不了仓库，「被检索却从没解决」这条信号到不了退休决定。
- **只保留事件驱动**（否决）。好处是因果链最短。代价是同一期的数字被切成碎片，趋势线要重拼，分母复核没有落点。
- **把语义那一半与机械化一半合成一个「无效探索次数」**（否决）。好处是面板上只有一个数。代价是两者强度与可比性不同——机械一半可由历史树离线重算，语义一半只能在线判断；合成后无法解读，也不能作为验收依据（外部研究也不支持把历史抽象成洞见再注入）。
- **让 agent 自动判定现场结局**（否决）。好处是回报成本归零。代价是外部对照只能判断内容对不对，判断不了现场是否解决；现场特异性只有现场能给。
- **在面板里直接读期文件自行求和**（否决）。好处是不新增生成物。代价是取数出现两处实现，且面板的解析器是手写的、已被实测证明会把新键折进指标行。
- **把检索的查询串、topK 与分数写进轨迹**（否决）。好处是检索质量在线可算。代价是 live 轨迹没有「预期命中」这个真值，记下来的是候选集而不是对错；带真值的量尺已在离线侧（回放夹具与排序对照），再加一份自报的候选集只会多一处无法判读的数。
- **把 token 与耗时写进轨迹事件**（否决）。好处是轨迹自足、不必关联。代价是复制而非关联：真实账单在 harness 会话日志里，轨迹里那份是 agent 自报值，不一致时以哪个为准没有判据；正确做法是按 `session_id` 关联。
- **给案例加状态字段表达生命周期**（否决）。好处是与先验层对称。代价是同一件事在案例层有两个表达——目录位置与字段值，不一致时没有判据；现有机制是软退休加归档可复活。
- **把诊断标签扩成多个人工枚举**（否决）。好处是语义完整。代价是单次回报的选择成本上升，而反馈捕获在三期快照里都是 0；可机器派生的状态不该再问人一次。
- **把验证回放产物 `.s2-replay/` 收进主检出锚定表**（否决）。好处是跨 worktree 可见。代价是写入侧分散在四个脚本的散文路径里，只锚读侧会得到「写进 worktree、读主检出、报 0 条结算」，比现在各检出自洽更坏。

## 后果

- 好，因为条目级观测与知识变更同行：一次整理就能把自己的本机使用史带进仓库，不再需要单独一轮搬运。
- 好，因为「被选中」与「现场确认解决」在数据上分开，选中不再污染命中率。
- 好，因为开源类问题的结局可以自动查证、自动闭环，现场类问题仍保留人工通道，两条通道各自计、不合成一条准确率。
- 好，因为无效探索只落地可离线重算的一半，另一半如实标为在线判断，不做成一个无法解读的复合数。
- 好，因为指标的存在条件（五格）写成了可检查的清单，没有决定读的指标会被删掉而不是继续空转。
- 坏，因为期文件会变大，且新增一个段就要同步白名单、组装脚本、文档、面板标签与面板包，改动面比一个独立文件大。
- 坏，因为本台账按部署分家，跨机器的热点榜在只有一台部署有数据之前看不到。
- 坏，因为分步成本要接 harness 会话日志，两个数据源按 `session_id` 关联，关联失败时该会话的成本缺席（如实标缺席，不补估值）。
- 坏，因为外部自动对照只覆盖有上游锚点的案例；客户侧现网问题仍然只能等人工回报，学习环在那些问题上依旧没有分母。
- 坏，因为无效探索的打分在闸门满足前不写，面板上这一项会长期是「缺打分本体」。
